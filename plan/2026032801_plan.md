# 교회 기능 개발(feature_01) 요구사항 수행

## 1. 프롬프트 기록
- `AGENTS.md`를 먼저 참조
- `features/feature_01.md`에 대한 요구사항 수행

## 2. 분석한 내용
- 현재 프로젝트는 Next.js App Router 기반이며, 전역 상태는 Zustand(`src/store/app-store.ts`), 원격 저장은 Supabase(`src/lib/supabase-store.ts`)를 사용하고 있다.
- 현재 데이터 모델은 개인 단위 기능 중심이다. `supabase/schema.sql`에는 개인용 `plans`, `memos`, `prayers`, `favorite_verses`, `bible_grass`만 정의되어 있고, 교회/팀/가입 신청/역할을 위한 테이블은 아직 없다.
- 현재 성경읽기 계획 기능은 `/plans`, `/plans/add`, `/plans/[id]`, `/plans/[id]/edit` 경로와 `PlanRecord` 타입을 기준으로 동작하며, 개인 소유 `user_id` 기준으로만 조회/수정되도록 설계되어 있다.
- 현재 네비게이션에는 교회 진입점이 없다. 하단 탭(`src/components/layout/tab-bar.tsx`)과 마이페이지 메뉴(`src/app/mypage/page.tsx`) 모두 교회 관련 메뉴를 제공하지 않는다.
- 요구사항을 충족하려면 단순 UI 추가가 아니라 아래 범위의 확장이 함께 필요하다.
- 교회와 사용자 다대다 관계
- 교회와 팀 일대다 관계
- 교회 내부에서 사용자의 팀 소속 제약
- 교회/팀 공용 성경읽기 계획의 소유 범위(`church_id`, `team_id`)
- 슈퍼 관리자/부관리자 권한 및 가입 신청 승인 흐름
- 특히 현재 Supabase RLS는 대부분 `auth.uid() = user_id` 형태의 개인 소유 정책이므로, 교회 공유 데이터에 맞는 접근 정책을 새로 설계해야 한다.
- 요구사항에는 부관리자 목록을 문자열 필드(`"9930, 42930, 2302"` 형태)로 저장하라는 명시가 있다. 구현 시 요구사항을 따르되, 실제 권한 판별과 데이터 정합성 측면에서 다대다 멤버십 테이블과의 역할 분담을 명확히 해야 한다.
- 현재 프로젝트에는 다른 사용자의 공개 이름을 안전하게 조회할 수 있는 `profiles` 계층이 없다. `auth.users`는 일반 클라이언트에서 직접 조회하기 어렵기 때문에, 교회 회원 리스트/가입 신청 리스트/팀장 표시를 위해 공개 프로필 테이블 또는 동등한 공개 조회 계층이 추가로 필요하다.
- 가장 중요한 구조 변경 포인트는 공용 성경읽기 계획이다. 현재 `plans.goal_status`, `current_read_count`, `goal_percent`는 계획 1건에 진행 상태가 1세트만 존재하는 구조인데, 요구사항은 공용 계획 안에서 여러 사용자의 개별 진행도와 평균 진행도를 요구한다. 따라서 `계획 메타 정보`와 `사용자별 진행 상태`를 분리하는 테이블이 필요하다.
- 요구사항 양이 커서 1회 작업으로는 스키마, 타입, 상태관리, 화면, 권한, 테스트까지 폭넓게 바뀔 가능성이 높다.

### 권장 ERD 초안

#### 1) `public.user_profiles`
- 목적: 교회 회원/팀원/가입 신청자 표시용 공개 사용자 정보 저장
- 권장 컬럼
  - `user_id uuid primary key references auth.users(id) on delete cascade`
  - `display_name text not null default ''`
  - `email text`
  - `avatar_url text`
  - `created_at timestamptz not null default timezone('utc', now())`
  - `updated_at timestamptz not null default timezone('utc', now())`
- 비고
  - 현재 로그인한 사용자의 `user_metadata`를 바탕으로 로그인/동기화 시 upsert
  - 교회 회원 리스트는 이 테이블과 조인해서 표시

#### 2) `public.churches`
- 목적: 교회 기본 정보와 관리자 메타데이터 저장
- 권장 컬럼
  - `id bigint generated by default as identity primary key`
  - `name text not null`
  - `created_at timestamptz not null default timezone('utc', now())`
  - `updated_at timestamptz not null default timezone('utc', now())`
  - `created_by_user_id uuid not null references auth.users(id) on delete restrict`
  - `super_admin_user_id uuid not null references auth.users(id) on delete restrict`
  - `member_count integer not null default 0`
  - `deputy_admin_user_ids text not null default ''`
- 비고
  - 요구사항의 부관리자 ID 문자열 저장 조건을 이 필드에서 충족
  - 실제 권한 판별의 기준은 문자열보다는 멤버십 테이블의 역할 컬럼으로 두고, `deputy_admin_user_ids`는 동기화되는 캐시 필드로 유지하는 것이 안전
  - 교회명은 일단 중복 허용으로 가정하고, 검색 결과 리스트에서 구분하는 방향이 현실적

#### 3) `public.teams`
- 목적: 교회 하위 팀 저장
- 권장 컬럼
  - `id bigint generated by default as identity primary key`
  - `church_id bigint not null references public.churches(id) on delete cascade`
  - `name text not null`
  - `created_at timestamptz not null default timezone('utc', now())`
  - `updated_at timestamptz not null default timezone('utc', now())`
  - `created_by_user_id uuid not null references auth.users(id) on delete restrict`
  - `leader_user_id uuid references auth.users(id) on delete set null`
- 권장 인덱스/제약
  - `unique (church_id, name)`
  - `(church_id, id)` 유니크 인덱스를 추가해서 교회 멤버십의 `team_id`가 같은 교회 팀만 가리키도록 복합 참조 기반을 만들 수 있음

#### 4) `public.church_memberships`
- 목적: 교회와 사용자 다대다 관계 및 역할/팀 소속 저장
- 권장 컬럼
  - `church_id bigint not null references public.churches(id) on delete cascade`
  - `user_id uuid not null references auth.users(id) on delete cascade`
  - `role text not null default 'member'`
  - `team_id bigint null`
  - `joined_at timestamptz not null default timezone('utc', now())`
  - `created_by_user_id uuid references auth.users(id) on delete set null`
  - `updated_at timestamptz not null default timezone('utc', now())`
- 권장 제약
  - `primary key (church_id, user_id)`
  - `check (role in ('super_admin', 'deputy_admin', 'member'))`
  - `(church_id, team_id) -> teams(church_id, id)` 형태의 복합 참조를 사용해 다른 교회 팀으로 잘못 연결되는 것을 방지
- 설계 이유
  - 요구사항상 사용자 1명은 교회 내에서 팀 1개에만 속할 수 있으므로, 별도의 `team_memberships` 테이블보다 `church_memberships.team_id` 하나로 관리하는 편이 단순하고 제약을 걸기 쉽다
  - `team_id`가 `null`이면 `교회 > user` 구조, 값이 있으면 `교회 > 팀 > user` 구조를 자연스럽게 표현할 수 있다

#### 5) `public.church_join_requests`
- 목적: 교회 가입 신청 및 승인/거절 이력 저장
- 권장 컬럼
  - `id bigint generated by default as identity primary key`
  - `church_id bigint not null references public.churches(id) on delete cascade`
  - `requester_user_id uuid not null references auth.users(id) on delete cascade`
  - `status text not null default 'pending'`
  - `requested_at timestamptz not null default timezone('utc', now())`
  - `processed_at timestamptz`
  - `processed_by_user_id uuid references auth.users(id) on delete set null`
- 권장 제약
  - `check (status in ('pending', 'approved', 'rejected', 'cancelled'))`
  - `pending` 상태에 대해서만 `(church_id, requester_user_id)` partial unique index
- 설계 이유
  - 승인/거절 이력을 남기면서도 같은 사용자가 중복으로 대기 신청을 여러 건 쌓는 것을 막을 수 있다

#### 6) 기존 `public.plans` 확장
- 목적: 개인 계획과 교회/팀 공용 계획을 같은 도메인에서 관리
- 권장 추가 컬럼
  - `church_id bigint null references public.churches(id) on delete cascade`
  - `team_id bigint null references public.teams(id) on delete cascade`
- 권장 의미
  - 개인 계획: `church_id is null and team_id is null`
  - 교회 공용 계획: `church_id is not null and team_id is null`
  - 팀 공용 계획: `church_id is not null and team_id is not null`
- 비고
  - 현재 `plans.user_id`는 계획 생성자 또는 소유자 개념으로 유지 가능
  - 팀 공용 계획은 반드시 같은 교회의 팀만 연결되도록 앱 로직과 제약을 같이 둬야 한다

#### 7) `public.plan_progresses`
- 목적: 공용 계획 안에서 사용자별 진행 상태 저장
- 권장 컬럼
  - `plan_id bigint not null references public.plans(id) on delete cascade`
  - `user_id uuid not null references auth.users(id) on delete cascade`
  - `goal_status jsonb not null default '[]'::jsonb`
  - `current_read_count integer not null default 0`
  - `goal_percent double precision not null default 0`
  - `read_count_per_day double precision not null default 0`
  - `rest_day integer not null default 0`
  - `created_at timestamptz not null default timezone('utc', now())`
  - `updated_at timestamptz not null default timezone('utc', now())`
- 권장 제약
  - `primary key (plan_id, user_id)`
- 설계 이유
  - 공용 계획 상세에서 사용자별 진행도와 평균 진행도를 보여주려면 별도 진행 테이블이 필요하다
  - 장기적으로는 개인 계획도 동일한 구조로 맞추면 일관성이 높아진다

### 관계 요약

- `churches.super_admin_user_id -> auth.users.id`
- `teams.church_id -> churches.id`
- `teams.leader_user_id -> auth.users.id`

- `church_memberships.team_id -> teams.id`

- `plans.team_id -> teams.id`

- `plan_progresses.user_id -> auth.users.id`

### 권한 및 동작 설계 포인트
- `churches`
  - 검색 기능 때문에 최소한 인증 사용자에게 교회명 검색은 허용되어야 한다
  - 교회 상세의 민감 정보는 멤버만 보이게 할지, 전체 공개로 둘지 정책을 정해야 한다
- `church_memberships`
  - 같은 교회 멤버만 회원 리스트를 조회 가능
  - 슈퍼 관리자는 부관리자 권한 부여/회수 가능
  - 부관리자는 회원 승인 가능하지만 슈퍼 관리자 권한 변경은 불가
- `church_join_requests`
  - 신청자는 자신의 신청 상태를 볼 수 있어야 한다
  - 슈퍼 관리자/부관리자는 자신이 관리하는 교회의 신청 목록만 볼 수 있어야 한다
- `plans`
  - 개인 계획은 기존처럼 본인만 수정
  - 교회 공용 계획은 슈퍼 관리자만 수정 가능
  - 팀 공용 계획은 슈퍼 관리자와 부관리자가 수정 가능
  - 부관리자가 교회 전체 계획(`church_id`만 있고 `team_id`는 null)을 수정하지 못하도록 DB 레벨 또는 RPC 레벨에서 막는 것이 안전하다

### 추가 고려사항
- 가입 승인 시 처리
  - `church_join_requests` 상태 변경
  - `church_memberships` 생성
  - `churches.member_count` 갱신
  - 필요 시 기존 교회 공용 계획에 대한 `plan_progresses` 자동 생성
- 팀 배정 또는 팀 이동 시 처리
  - `church_memberships.team_id` 갱신
  - 해당 팀의 기존 공용 계획들에 대한 `plan_progresses` 생성 또는 재정리 정책 필요
- 공용 계획 생성 시 처리
  - 현재 대상 멤버 전원에 대한 `plan_progresses`를 생성해야 평균 진행도/개인 진행도 화면이 즉시 동작한다
- 멤버 탈퇴/추방 시 처리
  - 팀 공용 계획과 교회 공용 계획의 기존 개인 진행 데이터를 보존할지 삭제할지 정책이 필요하다
  - 초기 구현에서는 조회 대상에서 제외하되 데이터는 남기는 방향이 가장 안전하다
- 데이터 접근 전략
  - 기존 개인 데이터(`favorites`, `memos`, `prayers`, 개인 `plans`)는 지금처럼 Zustand persisted state 유지 가능
  - 교회/팀/가입 신청/공용 계획처럼 여러 사용자가 공유하는 데이터는 stale 문제가 크므로, 전역 persisted store보다는 `useCustomQuery` 기반 페이지 조회가 더 적합하다
- UI 진입점 전략
  - 요구사항의 `교회 메뉴 추가`는 하단 탭에 `/churches`를 추가하는 것이 가장 직접적이다
  - 개인용 계획(`/plans`)은 유지하고, 교회 공용 계획은 `/churches/...` 하위에서 분리하는 편이 역할과 범위가 명확하다
- 마이그레이션 전략
  - 기존 `plans` 데이터는 기본적으로 `church_id/team_id = null`인 개인 계획으로 유지
  - 새 구조 도입 후에도 기존 개인 기능이 깨지지 않도록 점진 확장이 필요하다

## 3. 해당 프롬프트를 완수하기 위한 계획
1. DB/ERD 구현
- `supabase/schema.sql`에 `user_profiles`, `churches`, `teams`, `church_memberships`, `church_join_requests`, `plan_progresses`를 추가한다.
- 기존 `plans`에 `church_id`, `team_id`를 추가하고, 개인/교회/팀 계획을 구분할 수 있게 한다.
- 인덱스, 체크 제약, RLS 초안을 함께 반영하고, 관리자 권한 변경/가입 승인/공용 계획 생성처럼 원자성이 필요한 동작은 RPC 또는 안전한 write 로직으로 묶는다.

2. 프론트 도메인 계층 구현
- 개인 persisted 상태와 교회 공유 상태를 분리한다.
- 개인 데이터는 기존 Zustand 흐름을 유지하고, 교회/팀/가입 신청/공용 계획은 `useCustomQuery` 기반 조회 훅과 Supabase 액션 함수로 구성한다.
- 공용 계획은 `plan metadata + plan_progresses` 구조를 반영해 타입과 계산 함수를 재정비한다.

3. 화면 및 라우팅 구현
- 하단 탭에 `교회` 메뉴를 추가하고 `/churches` 페이지에서 내 교회 목록, 교회명 검색, 가입 신청을 제공한다.
- `/churches/[id]`에 회원 리스트/성경읽기 계획/팀 리스트 탭을 구현한다.
- `/churches/[id]/plans/...`, `/churches/[id]/teams/[teamId]/...` 경로에서 공용 계획 생성/수정/상세를 제공하고, 역할별 버튼 노출과 수정 제한을 반영한다.
- 공용 계획 상세에서는 팀 정보, 팀원 목록, 사용자별 진행도, 평균 진행도를 노출한다.

4. 검증 및 회귀 확인
- `eslint`와 `next build` 기준으로 검증한다.
- 기존 개인 계획 기능이 유지되는지, 교회 권한 분기가 UI와 데이터 레벨에서 함께 막히는지 확인한다.

## 4. 사용자가 추가로 기획해야 하는 사항, 보충해야 하는 사항
- 팀장(`leader_user_id`)을 언제, 어떤 화면에서 지정/변경할지 추가 기획이 필요하다. 이번 구현에서는 팀 생성과 팀 기반 계획까지 우선 연결했고, 팀장은 nullable 구조로 열어두었다.
- 교회 상세를 비회원에게 어디까지 노출할지 정책이 더 필요하다. 현재는 교회 검색은 가능하고, 실제 상세/회원/팀/공용 계획 데이터는 RLS 기준으로 멤버 중심 접근이 되도록 구성했다.
- 멤버 탈퇴/강퇴, 가입 신청 취소, 팀 재배치, 팀장 변경 같은 운영 기능은 후속 기획이 필요하다.
- 팀 계획을 교회 내 비팀원도 볼 수 있게 할지, 팀원만 보게 할지에 대한 정책은 더 명확히 정하면 좋다. 현재 구현은 같은 교회 멤버가 조회 가능한 방향으로 정리했다.

- 검증 결과 `npm run lint`, `npm run build` 모두 통과했다.

## 7. 사용자가 해야하는 추가 작업
- `supabase/schema.sql`의 변경사항을 실제 Supabase DB에 반영해야 한다. 이 작업 전에는 교회 기능이 정상 동작하지 않는다.
- 이미 로그인된 세션이 있다면 스키마 반영 후 다시 로그인해서 `user_profiles` 동기화가 한 번 실행되게 하는 것이 안전하다.
- 필요하다면 운영 정책에 맞춰 가입 신청 취소, 팀장 자동 승계, 교회 삭제/권한 이관 같은 운영 기능을 후속으로 추가 기획해야 한다.

## 추가 반영 사항
- 팀장 지정/변경 기능 추가
  - 교회 상세의 `팀 리스트` 탭에서 팀별 팀장을 선택하고 저장할 수 있게 구현했다.
  - 팀장은 해당 팀에 실제로 속한 멤버만 지정되도록 DB RPC(`set_team_leader`)에서 검증한다.
- 멤버 팀 배정/이동 기능 추가
  - 교회 상세의 `회원 리스트` 탭에서 멤버별 팀을 선택하고 저장할 수 있게 구현했다.
  - 슈퍼 관리자는 전체 멤버를, 부관리자는 일반 멤버만 팀 배정/이동할 수 있도록 제한했다.
  - 팀 이동 시 기존 팀의 팀장이던 사용자가 팀을 떠나면 팀장 값이 자동으로 해제되도록 트리거를 추가했다.
- 멤버 내보내기/자기 탈퇴 기능 추가
  - 교회 상세의 `회원 리스트` 탭에서 관리자 권한으로 멤버를 교회에서 내보낼 수 있게 구현했다.
  - 본인은 `교회 나가기` 버튼으로 탈퇴할 수 있게 구현했다.
  - 슈퍼 관리자는 교회를 바로 떠날 수 없도록 DB RPC(`remove_church_member`)에서 차단했다.
  - 부관리자는 일반 멤버만 내보낼 수 있고, 슈퍼 관리자는 슈퍼 관리자를 제외한 멤버를 내보낼 수 있도록 제한했다.
- DB 안전장치 추가
  - `set_team_leader`, `set_church_member_team`, `remove_church_member` RPC를 추가해 권한과 데이터 정합성을 DB 레벨에서 검증하도록 보강했다.
  - 멤버 이동/삭제 시 팀장 무결성을 유지하는 `cleanup_team_leader_on_membership_change` 트리거를 추가했다.
- 검증
  - 추가 반영 후에도 `npm run lint`, `npm run build`를 다시 실행했고 모두 통과했다.
